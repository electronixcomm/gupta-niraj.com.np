Managing and verifying switch configuration

Building a config (Unit 2.3) is only half the job. This unit is about the other half: confirming the switch is actually doing what we configured, moving configuration safely between memory and storage, the specific ways a password or privilege level goes wrong, and what our real options are if every login credential is lost at once.

Console, Telnet, and SSH: how you're actually connecting

Before verifying or managing anything, it's worth being precise about what kind of connection is in use — because one of the three has properties the other two simply don't have.

MethodMediumSecurityBaud rate applies?
ConsolePhysical RS-232 serial cable (or USB-to-serial) direct to the deviceNot encrypted — security comes from requiring physical presence, not from the protocolYes — it's a genuine serial link with a configurable line speed
TelnetTCP/IP network, TCP port 23Unencrypted — usernames, passwords, and commands travel in clear textNo — it rides over Ethernet/IP, not a serial line
SSHTCP/IP network, TCP port 22Encrypted (the RSA-key setup from Unit 2.3)No — same reason as Telnet
"Baud rate" is a console-only concept Telnet and SSH sessions travel over an Ethernet/IP link, which is measured in bits per second at the interface (10/100/1000 Mbps etc.), not baud.

On the console line itself, the default and minimum matter for different reasons:

Baud rateNote
9600 bpsThe factory default on essentially every Cisco IOS device — this is what a terminal program should be set to before a console cable is even plugged in for the first time.
300 bpsThe lowest speed most platforms allow via line console 0 → speed 300 (some newer platforms floor at 1200 bps instead). Essentially never used in practice — only relevant to know it's the floor, not the default.
19200 / 38400 / 57600 / 115200 bpsHigher speeds sometimes set on purpose when console logging is very verbose (e.g. debug output), so the terminal isn't the bottleneck — both ends must be changed to match, or the session turns to garbled text.

Verifying: how do you know it actually worked?

A command being accepted at the prompt is not the same as the feature behind it actually functioning — the SSH example from Unit 2.3 is exactly this problem. Verification is a separate, deliberate step, not something to assume.

Interface status vs. line protocol: two separate layers

show interfaces and show ip interface brief report interface health as two independent states— thus conflating them as one of the most common early troubleshooting mistakes:

  • Status (Layer 1 / physical) — is there a working electrical or optical signal on the wire right now? Controlled by the cable, the NIC/transceiver on both ends, and whether the port has been administratively shut down.
  • Line protocol (Layer 2 / data-link) — are the two ends actually exchanging and agreeing on data-link control traffic (keepalives, encapsulation, negotiation)? This can only come up once Layer 1 is already up — it depends on it.
Status / ProtocolWhat it meansTypical cause
up / upFully operational at both layers.Normal working link — nothing to do.
administratively down / downThe interface has been manually disabled.Someone ran shutdown on it — no shutdown re-enables it.
down / downNo usable physical signal at all.Unplugged or bad cable, dead port/transceiver on either end, or the remote device is powered off.
up / downLayer 1 is fine, but the two ends aren't agreeing at Layer 2. The interface can sense a signal but nothing useful is being exchanged.Encapsulation mismatch, keepalives disabled on one side, duplex/speed mismatch, a WAN clocking issue, or (on switch trunks) a VLAN/native-VLAN mismatch.
up / down is the diagnostic case, not a random combination Because line protocol depends on Layer 1 already being up, up / down is the one state that specifically says "the cable is fine, the problem is in how the two ends are configured to talk to each other" — not a wiring issue. It's the single most useful state to recognize on sight, since it immediately rules out half of the usual suspects (bad cable, dead port, remote device down).

show interfaces status reports the same underlying reality, but on Catalyst switches it collapses both layers into one combined Status column instead of two separate fields — worth knowing so the two commands aren't read as contradicting each other:

Status valueLayer 1 / Layer 2 equivalentMeaning
connectedup / upLink is up and passing traffic normally.
notconnectdown / downNo cable, or nothing responding on the other end.
disabledadministratively down / downThe port has been shut down in software.
err-disabledup (was) / down, forced offThe switch shut the port down itself after detecting a violation — most often port security, a BPDU guard trigger, or a storm-control threshold. Recovers with shutdown / no shutdown once the cause is fixed, or automatically if errdisable recovery is configured.
inactiveadministratively reachable, logically excludedThe port is assigned to a VLAN that doesn't exist (or has been deleted) on this switch — a config problem, not a cabling one.
monitoring—The port is a SPAN/monitor session destination, so it doesn't participate in normal switching.

The configuration lifecycle

Three places a configuration can live, and the commands that move it between them.

running-configRAM · active now · volatile
⇆copy run start /
copy start run
startup-configNVRAM · loads on boot
⇆copy run tftp: /
copy tftp: start
TFTP/SCP serveroff-device backup

Everything configured lives in running-config first. copy running-config startup-config (Unit 2.3's write memory) commits it to survive a reboot. Backing up to an external TFTP/SCP server is the step most labs skip and most real networks cannot skip — it's the only copy that survives the device itself failing.

Managing configuration: the commands

Click a step to expand it.

copy running-config startup-config
copy startup-config running-config

The first commits current work so it survives a reboot. The second is used far less often, and behaves differently than most people expect — see the caution section below before relying on it.

copy running-config tftp:
copy startup-config tftp:
copy running-config flash:backup-2082-06-01.cfg

Sends a copy of the config to a TFTP server (prompts for server IP and filename), or snapshots it locally to flash under a distinct filename. A local flash copy is better than nothing, but it's still on the same physical device — it doesn't help if the switch itself is lost or bricked.

erase startup-config
delete vlan.dat
reload

Used to return a lab switch to factory defaults between exercises. All three lines matter — see the caution section for why erase startup-config alone is a common trap.

show running-config
show startup-config

Run both, side by side, before saving. If they already match, there's nothing new to lose; if they differ, that difference is exactly what a reload would discard. This ten-second habit is the direct fix for the save-typo scenario from Unit 2.3.

Caution

A short list of the specific mistakes that turn a routine maintenance task into an outage — each one easy to avoid once you know it's there.

!

copy startup-config running-config merges, it does not replace

This command layers the saved config on top of what's already running — it does not clear the current running-config first. Any interface or line you configured since the last save, but never intended to keep, stays active. If the goal is "throw away my unsaved changes and go back to the last save," a reload is the reliable way to do it, not this command.

!

erase startup-config does not touch the VLAN database

On most Catalyst switches, VLAN information is stored separately, in vlan.dat on flash — not inside startup-config. Erasing startup-config and reloading can still leave old VLANs in place, which is confusing when the goal was a clean factory-default switch. delete vlan.dat is the extra step that actually clears it.

!

A reload discards everything unsaved, instantly and without a second prompt in scripts

If a session is run non-interactively or piped from a script, reload can execute past a confirmation prompt. Get in the habit of running show running-config vs show startup-config immediately before any reload, exactly as in Step 4 above.

!

Changing VTY or SSH settings from a remote SSH session can lock you out

If a change to line vty or the SSH configuration is made over a remote session, and it's wrong, the session can drop before it's possible to fix — and if there's no working console access, the only recovery path is a password-recovery procedure that typically needs physical access and a reboot. Test access-affecting changes from the console when possible, or keep a second session open until the new settings are confirmed working.

When the password or privilege level is configured wrong

Cisco IOS has 16 privilege levels (0–15). Level 1 is ordinary user EXEC, level 15 is full privileged EXEC, and 2–14 exist but sit empty until an administrator deliberately assigns commands to them. Most of the trouble here isn't exotic — it's a handful of specific, well-known traps that produce either an unintended open door or an unintended lockout.

0disabled & a few basics
→default line
login
1user EXEC · show only
→enable /
enable secret
15privileged EXEC · full config

Levels 2–14 are real but inert by default — nothing runs there until commands are explicitly moved down with privilege exec level <n> <command>. A login that lands at level 5 with nothing assigned to level 5 isn't broken; it's just an empty room.

enable secret always wins over enable password If both are configured, IOS uses enable secret (MD5, or type 8/9 on newer platforms) and silently ignores enable password. Typing the old enable password after someone has since set an enable secret will simply fail — the account isn't broken, the wrong credential is being tried. service password-encryption is worth mentioning here too: it only obfuscates the weak, reversible enable password and line passwords with a trivial Vigenère-style cipher — it is not real encryption and should never be treated as a security control on its own.
!

A line password without login prompts for nothing

Setting password cisco123 under a line does nothing on its own — IOS only enforces it once login (or login local) is also configured on that line. Forgetting the second command is a genuine open door, not a minor oversight: anyone reaching that line gets straight in, no prompt, no password.

!

login local with no local usernames locks the line, not just the wrong password

Switching a line to login local before any username ... secret ... account exists doesn't fall back to a line password — it rejects every login attempt outright, because there's no local database to check against. Applied to vty lines from a remote session, this is an instant, self-inflicted lockout of remote access.

!

Assigning privilege level 15 directly to a line skips authentication entirely

privilege level 15 configured on a line (console or vty) means anyone who reaches that line lands in full privileged EXEC the moment login succeeds — or, combined with the mistake above, the moment they connect at all. It's a common misreading of "give this user full access" that actually means "give this connection point full access, regardless of who uses it."

!

Forgetting enable secret is not the same as forgetting a line password

If the console/line password is known but the enable secret isn't, the switch is still reachable and still usable at user EXEC — show commands, ping, basic diagnostics all work. What's lost is the ability to enter configuration mode. Because enable secret is a one-way hash, it cannot be recovered or decrypted from the config file — it can only be reset, and that requires the password-recovery procedure below.

Forgot console and SSH credentials entirely — is the hardware still usable?

Short answer: yes. Losing every login credential is a configuration and access problem, not a hardware failure — nothing about the switch itself is damaged, and Cisco's password-recovery procedure exists specifically for this situation. The real constraint isn't the hardware, it's physical access.

The catch is physical access, not the hardware Password recovery on Cisco IOS switches works through the console port and a reboot — it cannot be done over SSH or Telnet, precisely because if it could, it wouldn't be much of a security boundary. So the real question is never "is the switch dead," it's "can someone get a console cable to it." A switch sitting in a locked, unreachable rack in another city is unmanageable until someone is physically present — but the moment console access exists again, the device is fully recoverable.

Connect a console cable, open a terminal session, then power-cycle the switch. Watch the boot output closely — the next step has a narrow window.

(hold the Mode button, or send a break signal,
within the first ~15–60 seconds of boot,
depending on the platform)

This drops the switch into ROMMON (or a bootloader "switch:" prompt on newer Catalyst platforms) before it loads any saved configuration — the exact key sequence is platform-specific, so check the model's recovery guide.

flash_init
rename flash:config.text flash:config.text.old
boot

On routers, the equivalent is changing the config register to 0x2142 before booting. Either way, the goal is the same: start IOS without loading the saved passwords, landing in enable mode with no credential required.

rename flash:config.text.old flash:config.text
copy flash:config.text running-config
enable secret <new-secret>
line con 0
 password <new-password>
 login
line vty 0 4
 login local
username <admin> secret <new-secret>

Bring the original configuration back into running-config first — otherwise VLANs, interface settings, and everything else configured is lost, not just the passwords — then overwrite only the credentials.

copy running-config startup-config
reload

Confirm login works with the new credentials before walking away — exactly the "verify before you trust it" habit from earlier in this unit.

!

no service password-recovery blocks this on purpose

Some organizations deliberately disable the ROMMON bypass with no service password-recovery, so that physical theft of a switch doesn't also hand over its configuration. If that command was set, the standard procedure above is blocked by design — recovery still exists, but it typically means erasing the entire configuration and reloading from factory defaults, rather than a clean password reset. The hardware still isn't damaged; the accumulated configuration is what's sacrificed.

!

The switch keeps forwarding traffic the whole time

Losing every login credential doesn't stop the switch from doing its job — the data plane keeps switching frames based on whatever configuration is already running. What's lost is the ability to manage it: no new VLANs, no config changes, no visibility, until access is recovered. That's an availability risk for administrators, not for the traffic already flowing through it.

How production networks avoid ever reaching this point

Centralized AAA (TACACS+/RADIUS) means one lost or forgotten credential doesn't lock out the whole device — a break-glass local account is kept for exactly this case. Out-of-band console servers give remote console access without anyone driving to a site. And configs are backed up off-box (per the lifecycle diagram above) so that even a full factory-reset recovery restores the device in minutes rather than starting from a blank switch.

Tips

Small habits that make the commands above faster and less error-prone day to day.

Filter long output instead of scrolling

Pipe any show command through | include, | section, or | begin to jump straight to the relevant lines.

show running-config | section line vty

Stop pagination during long output

terminal length 0 disables the --More-- prompt for the current session — useful before a long show tech-support or when logging a session to a file.

terminal length 0

Timestamp your own backups

A flash or TFTP filename like sw1-2082-06-01.cfg is far easier to reason about later than an unlabelled startup-config copy from an unknown date.

Save immediately after a change is confirmed working

Don't batch several changes and save once at the end — verify, then save, per change where practical. It keeps the gap between "known good" and "current" as small as possible.

Industry convention

How the same commands above tend to be used differently once a network is someone's actual job, not a lab exercise.

Hostname naming

Real networks rarely use ad-hoc names like UniGlobe_Main_Switch_1. A common pattern encodes site, role, and number — e.g. KTM-DC-SW01 for the first data-center switch in a Kathmandu site — so a hostname alone tells an engineer roughly what the device is and where.

Legal banner

banner motd is configured on essentially every production device to display an authorized-access-only warning before login — a legal and organizational expectation, not just a lab nicety.

Off-box backups, on a schedule

Manually running copy running-config tftp: after a change doesn't scale. Production networks typically automate this with tools like RANCID or Oxidized, or push configs into version control (git), so every change has a timestamped, diffable history independent of the device itself.

Change management

Access-affecting changes (VTY, ACLs, routing) are scheduled in a maintenance window, with the previous known-good config backed up and a rollback plan written down before the change is made — not improvised afterward if something breaks.

Centralized authentication

The local username ... secret account from Unit 2.3 is standard for a small lab, but production environments generally authenticate against a central AAA server (TACACS+ or RADIUS) instead, so access can be revoked for one person without touching every device's local config.
