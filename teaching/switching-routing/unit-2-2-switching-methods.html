How a switch decides when to forward a frame

Every switch faces the same trade-off: wait for more of the frame and forward it safely, or act early and forward it fast. The three switching methods are just three different answers to that trade-off — and the answer is decided by exactly how many bytes the switch reads before making its move.

Three methods, three amounts of patience

All three read the frame in the same order. They differ only in how early they stop reading and start forwarding.

Cut-through

reads 6 bytes*

Forwards the instant it has read the destination MAC address — the first field after the preamble. It doesn't wait for the rest of the frame to arrive at all.

No error checking is done, so a damaged or malformed frame can be forwarded before the switch has any way of knowing it's bad.

fastest no CRC check can forward runts

Fragment-free

reads 64 bytes

Waits for the first 64 bytes — the legal minimum frame size — before forwarding. Anything shorter than that can only be a collision fragment.

This filters out collision debris, but it still doesn't verify the FCS, so real data corruption inside a full-length frame slips through.

middle ground filters collisions no CRC check

Store-and-forward

reads entire frame

Buffers the whole frame, including the FCS trailer, then runs a CRC check. Corrupt or malformed frames are simply dropped.

The default on most modern switches — the latency cost is small at gigabit+ speeds, and it's the only method that actually verifies frame integrity.

slowest full CRC check most reliable

* 6 bytes of destination MAC, arriving right after the preamble and SFD — see the frame anatomy below.

Why cut-through can read the MAC without seeing the trailer

It works because the frame layout is fixed. The destination MAC always sits at the same offset — the switch doesn't need to see where the frame ends to know what's at the start.

Key point The Preamble and SFD are not counted toward the 64-byte minimum — that count starts at the Destination MAC and runs through the FCS. That's exactly the 18–1518 byte range you'll see quoted for Ethernet frame size.

Where "64 bytes" actually comes from

It isn't an arbitrary round number. It's tied to how long it takes a collision to be detected on a shared Ethernet segment.

On a half-duplex segment, CSMA/CD guarantees that if two devices transmit at once, the collision will be detected and jammed within the time it takes to send the first 64 bytes — the collision window. Once a transmission survives past that point, every device on the segment has already sensed the wire is busy, so the rest of the frame is safe from collision.

So fragment-free isn't inspecting the content of those 64 bytes for correctness — it's simply confirming the frame lived long enough to prove it isn't collision debris. Anything that dies before byte 64 is discarded as a runt.

Recap

1Cut-through forwards after reading just the destination MAC (6 bytes) — fast, but it can forward corrupted frames.
2Fragment-free waits for 64 bytes to rule out collision fragments — a middle ground on speed and safety.
3Store-and-forward waits for the whole frame and checks the FCS — slowest, but the only method that catches actual data corruption.
464 bytes is the Ethernet minimum frame size, sized to match the CSMA/CD collision window — not a round number picked for convenience.
5Padding is added by the sender's NIC, only when real data is under 46 bytes, and it's silently dropped by the receiver using the EtherType/length information.
