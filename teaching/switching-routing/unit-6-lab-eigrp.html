Unit 6 · Practical lab · Cisco Packet Tracer

EIGRP lab: the same network, a different protocol

This lab rebuilds NovaTech's internal routing on the exact topology and addressing from the OSPF lab — same routers, same subnets, same constraints — but using EIGRP instead. Building both on identical wiring makes the contrast concrete: what EIGRP configuration saves you, and what it asks you to watch for instead (AS numbers, K-values, auto-summary).

What you will practise

  • Configuring EIGRP with classful network statements and passive interfaces.
  • Connecting a router that cannot run EIGRP using static routes and redistribution.
  • Disabling auto-summary to fix a genuinely discontiguous network.
  • Verifying neighbors, the topology table, and the routing table; reading FD/RD.
  • Predicting the EIGRP composite metric from bandwidth and delay, and watching failover.
  • Finding and fixing EIGRP-specific faults, including a K-value mismatch.

Time: about 2.5 hours for Parts 1–3. Part 4 is optional, for a later session.

Part 1

Problem statement

NovaTech Pvt. Ltd. already migrated its internal routing to OSPF (see the companion lab). Management now wants the network team to evaluate EIGRP as an alternative on the same wiring, before deciding which to standardise on company-wide. Your job is to reconfigure the same four internal routers with EIGRP so that:

  • Every internal network can still reach every other internal network.
  • A link failure still reroutes traffic automatically.
  • All sites still reach the Internet server at 172.31.100.10 through HQ, with only one router knowing about the ISP.
  • No Hellos are sent toward PCs, servers, or Branch C, which cannot run EIGRP.
  • Branch C stays reachable from every site and can still reach the Internet.
Constraint: the ISP link is still static-only; HQ-R1 must inject a default route into EIGRP for the rest of the company.
Constraint: Branch C (BR-C) still cannot run a routing protocol. BR-B and BR-C keep their static routes; BR-B must inject Branch C's network into EIGRP.
Watch for: HQ-R1's LAN (172.16.20.0/24) and BR-A's LAN (172.16.50.0/24) are both subnets of the same classful network, 172.16.0.0/16, but they sit on opposite sides of the 10.0.0.0/8 backbone. That makes this a genuinely discontiguous network — exactly the condition that breaks EIGRP's default auto-summary behaviour.

  • Autonomous system number: 20 on every router — it must be identical everywhere, or no adjacency forms at all, even if every interface and subnet is correct.
  • Classful network 10.0.0.0 automatically enables every interface whose address starts with 10 — no wildcard mask needed, unlike OSPF.
  • The ISP links (172.31.0.0/30 and 172.31.0.4/30) are never in EIGRP. They don't match either network statement, so no wildcard-based exclusion is even needed.
  • no auto-summary is mandatory on HQ-R1, HQ-R2, BR-A, and BR-B. HQ-R1 and BR-A both advertise subnets of 172.16.0.0/16, and they are separated by the 10.0.0.0/8 backbone — a genuinely discontiguous network. Leaving auto-summary on will black-hole traffic between Server-HQ and PC-A.
  • Branch C: BR-C sends everything to BR-B with a static default route. BR-B has a static route to 192.168.30.0/24 and redistributes it into EIGRP with a metric, so every EIGRP router learns it automatically.

Task 3: Enable EIGRP

On HQ-R1, HQ-R2, BR-A and BR-B (not BR-C): start the process under AS 20, set a router ID, add a classful network statement for every attached major network, make LAN-facing interfaces passive, and disable auto-summary everywhere.

Why no auto-summary everywhere?
HQ-R1's 172.16.20.0/24 and BR-A's 172.16.50.0/24 are both subnets of 172.16.0.0/16, split across the 10.0.0.0/8 backbone. Left on, each site injects a competing 172.16.0.0/16 summary pointing to Null0, and the two LANs lose contact with each other.
HQ-R1 
configure terminal
router eigrp 20
 eigrp router-id 1.1.1.1
 network 10.0.0.0
 network 172.16.0.0
 passive-interface g0/2
 no auto-summary
end
HQ-R2 
configure terminal
router eigrp 20
 eigrp router-id 2.2.2.2
 network 10.0.0.0
 passive-interface g0/1
 no auto-summary
end
BR-A 
configure terminal
router eigrp 20
 eigrp router-id 3.3.3.3
 network 10.0.0.0
 network 172.16.0.0

end
BR-B 
configure terminal

As neighbors come up you should see console messages such as:

%DUAL-5-NBRCHANGE: IP-EIGRP(0) 20: Neighbor 10.0.0.2 (GigabitEthernet0/0) is up: new adjacency
BR-B's G0/1 is passive, not absent. The 10.0.4.0/30 link is still covered by network 10.0.0.0 and still advertised, but no Hellos go out toward BR-C, so no adjacency is even attempted there.

Task 4: Redistribute the default route and the Branch C network

EIGRP has no equivalent of OSPF's default-information originate — a non-EIGRP route, including a static default, is shared the same way any redistributed route is: with redistribute static and an explicit metric, since EIGRP cannot invent bandwidth/delay figures for a route it didn't learn itself.

HQ-R1: redistribute the default route 
configure terminal
router eigrp 20
 redistribute static metric 1544 2000 255 1 1500
end
BR-B: redistribute the Branch C route 
configure terminal
router eigrp 20
 redistribute static metric 1544 2000 255 1 1500
end

The five numbers after metric are bandwidth (Kbit), delay (tens of microseconds), reliability, load, and MTU — the same five factors the composite metric formula uses. Any reasonable values work here since the route doesn't compete on cost with anything else.

Check
  • On BR-A, show ip route includes D EX 192.168.30.0/24 and D*EX 0.0.0.0/0.
  • PC-C can ping the Internet-Server at 172.31.100.10 and PC-HQ at 10.1.10.10.

Task 6: Metric, path selection and failover

Using IOS defaults — GigabitEthernet: 1,000,000 Kbit / 10 µs delay; Serial (T1): 1,544 Kbit / 20,000 µs delay — and the default formula (metric = lowest bandwidth component along the path + sum of delay components):

6.1 Predict first

Path, HQ-R2 → 10.3.10.0/24WorkingTotal FD
via BR-A (all Gigabit)BW 2,560 + delay (256×3 hops)≈ 3,328
via BR-B (serial)BW 1,657,856 (serial dominates) + delay (512,000 + 256)≈ 2,170,112

Verify with show ip eigrp topology 10.3.10.0/24 and show ip route 10.3.10.0 — figures will vary slightly from these illustrative defaults if Packet Tracer reports different interface values; always confirm with show interfaces rather than assuming a textbook number.

6.2 Simulate a link failure

! On HQ-R2
configure terminal
interface g0/2
 shutdown
end
show ip route 10.3.10.0

The serial path should become the new successor within seconds, since it was already sitting in the topology table as a feasible successor. Restore the link with no shutdown afterward.

6.3 Challenge: unequal-cost load balancing

The two paths above are far from equal, so a very generous variance is needed to install both. On HQ-R2 and BR-B:

router eigrp 20
 variance 700
end
show ip route 10.3.10.0
What do you expect to see, and is this a good idea?
Both the Gigabit path and the serial path should appear as successors, sharing traffic in proportion to their metrics — so the fast path still carries far more. In practice a variance this large is a bad idea here: it sends meaningful traffic over a link hundreds of times slower, just to use it at all. Remove the variance afterward with no variance 700.

Task 7: Troubleshooting

A partner secretly introduces one fault below. Find it with only show commands, then fix it.

If an adjacency won't form, check in order
Interfaces down → AS numbers → K-values → passive interface → authentication.
Fault 1: Nobody can reach Branch C

Break it (BR-B): router eigrp 20 → no redistribute static

Symptom: BR-B can still ping PC-C, but no other site can.

Diagnose: no D EX 192.168.30.0/24 elsewhere; show ip protocols on BR-B no longer lists redistribution.

Fix: re-enter redistribute static metric 1544 2000 255 1 1500.

Fault 2: Branch A loses every EIGRP neighbor at once

Break it (BR-A): no router eigrp 20 then router eigrp 200 with the same network statements.

Symptom: show ip eigrp neighbors on BR-A is empty, even though interfaces are up.

Diagnose: show ip protocols on BR-A reports "eigrp 200" instead of "eigrp 20" — the AS number is wrong, and EIGRP ignores Hellos from a different AS entirely.

Fix: recreate the process under AS 20.

Fault 3: PC-C reaches its gateway and nothing else

Break it (BR-C): no ip route 0.0.0.0 0.0.0.0 10.0.4.1 then ip route 0.0.0.0 0.0.0.0 10.0.4.6

Symptom: PC-C can ping 192.168.30.1 but nothing beyond.

Diagnose: show ip route on BR-C has no S* entry — the next hop isn't on any connected network.

Fix: point the default route back at 10.0.4.1.

Fault 4: Branches reach each other but not the Internet

Break it (HQ-R1): router eigrp 20 → no redistribute static

Symptom: internal pings work; pings to 172.31.100.10 fail everywhere except Server-HQ, which sits behind HQ-R1 directly.

Diagnose: no D*EX 0.0.0.0/0 on branch routers.

Fix: re-enter redistribute static metric 1544 2000 255 1 1500.

Fault 5: Branch A won't form a single adjacency

Break it (BR-A): router eigrp 20 → metric weights 0 1 1 1 0 0

Symptom: BR-A loses every neighbor, even though AS numbers and addressing are correct everywhere.

Diagnose: show ip protocols on BR-A shows K1=1, K2=1, K3=1, K4=0, K5=0 — K2 doesn't match the rest of the network's K1=1, K2=0, K3=1, K4=0, K5=0. K-values must be identical to form an adjacency, and this is easy to miss because it doesn't show up as an addressing or AS problem.

Fix: metric weights 0 1 0 1 0 0 to restore the defaults.

Fault 6: Server-HQ and PC-A stop reaching each other, everything else is fine

Break it (BR-A): router eigrp 20 → auto-summary

Symptom: HQ-R1 and BR-A can each reach every 10.x network, but Server-HQ (172.16.20.0/24) and PC-A (172.16.50.0/24) can no longer reach each other.

Diagnose: show ip route on BR-A shows D 172.16.0.0/16 is a summary, 00:00:14, Null0 — BR-A is now summarizing its own 172.16.50.0/24 to the whole classful network and discarding anything inside it that isn't actually local, which silently drops traffic for 172.16.20.0/24.

Fix: no auto-summary.

Part 4 · for later practice

Optional extension: EIGRPv6

Once IPv6 addressing has been assigned to this same topology, EIGRPv6 is enabled per interface rather than with network statements:

! Every EIGRP-speaking router
configure terminal
ipv6 unicast-routing
ipv6 router eigrp 20
 no shutdown
 router-id 1.1.1.1
exit
interface g0/0
 ipv6 eigrp 20
interface g0/1
 ipv6 eigrp 20
! repeat per interface, skipping links toward BR-C and the ISP

There's no auto-summary setting and no passive-interface puzzle to solve: an interface not enabled with ipv6 eigrp 20 is simply outside the process. Verify with show ipv6 eigrp neighbors, show ipv6 eigrp topology, and show ipv6 route eigrp — next-hop addresses will always be link-local (FE80::...), never the routed address.

Part 5

Reflection questions

1. Why did EIGRP need no wildcard masks where OSPF did?
EIGRP's classful network 10.0.0.0 enables every interface whose address falls anywhere in 10.0.0.0/8, with no finer control offered or needed for this design. OSPF's wildcard lets you match an exact subnet, which is why it was used there to keep the ISP links out precisely.
2. Why wasn't auto-summary a problem in the OSPF lab, but is one here?
OSPF doesn't auto-summarize at all — it advertises exactly the subnets in its network statements. EIGRP's classic behavior collapses subnets to their classful boundary automatically, which breaks the moment the same classful network appears on both sides of a discontiguous backbone, as 172.16.0.0/16 does here.
3. Why does redistributing the default route need an explicit metric here, but OSPF just needed default-information originate?
OSPF's command exists specifically to inject a default route with a sensible built-in cost. EIGRP's redistribution is generic — any non-EIGRP source needs bandwidth, delay, reliability, load, and MTU supplied by hand, because EIGRP has no way to measure those for a route it didn't calculate itself.
4. If HQ-R2's link to BR-A fails, how does EIGRP reroute traffic to 172.16.50.0/24 compared to how OSPF would?
Both converge quickly, but EIGRP likely already has the serial-path route sitting in its topology table as a feasible successor, ready to install the instant the successor disappears — no recalculation needed. OSPF must rerun its SPF algorithm against the updated link-state database before it can choose a new path.
5. BR-C still can't run EIGRP. Did anything about its role change from the OSPF lab?
No — the static-route relationship with BR-B is identical regardless of which IGP runs elsewhere. BR-C never needs to know which protocol the rest of the network uses.
