Basic switch configuration: hostname, management IP, secured access, and SSH

A switch forwards frames with zero configuration — that's the whole point of the MAC table unit. Everything on this page is a different problem: how do you, the administrator, safely log in, identify the device, and manage it remotely. Built from a real run against UniGlobe_Main_Switch_1.

Why configure anything at all?

Out of the box, a switch already learns MAC addresses and forwards frames — no admin action required, as the companion page on the MAC address table shows. But an unconfigured switch has no identity, no IP address, no password on its console, and no way to be reached remotely. This section is about the small, standard set of commands that turn a bare switch into one that's identifiable, reachable, and locked down.

Every command below was actually run against UniGlobe_Main_Switch_1 in this lab, in this order.

The mode ladder

Cisco IOS commands are only accepted in the right mode. Almost every mistake beginners make — a command "not found," or the wrong prompt showing up — is really just being in the wrong mode.

Switch>
User EXEC mode. Very limited — mostly just show and ping. This is where you land right after login.
Switch#
Privileged EXEC mode. Full visibility (all show commands) and the gateway into configuration. enable (shorthand: en)
Switch(config)#
Global configuration mode. Device-wide settings — hostname, passwords, global services. configure terminal (shorthand: conf t)
Switch(config-if)# / (config-line)#
Sub-modes. One specific interface (interface vlan 1) or one specific line (line console 0, line vty 0 15) at a time. exit steps back up one level.

The configuration, step by step

Click a step to expand it. Together these eight steps produce the full running-config for UniGlobe_Main_Switch_1.

hostname UniGlobe_Main_Switch_1

Renames the switch from the factory default "Switch". Purely cosmetic on a single device, but essential the moment you're managing more than one — every prompt, log entry, and SSH session identifies itself by hostname.

interface vlan 1
 ip address 192.168.1.2 255.255.255.0
 no shutdown
exit
ip default-gateway 192.168.1.1

On a switch, an IP address lives on a virtual interface (the SVI, Vlan1) rather than a physical port — the switch itself isn't routing traffic, it just needs one address for management. SVIs are administratively down by default, so no shutdown is required to bring it up. ip default-gateway lets the switch itself (not hosts behind it) reach devices outside 192.168.1.0/24 — useful for things like remote syslog or NTP.

line console 0
 password Nepal123
 login
 exec-timeout 5 0
exit

password alone only stores a value — login is what actually tells the switch to enforce it on incoming console sessions. exec-timeout 5 0 auto-logs out an idle session after 5 minutes 0 seconds, so a console cable left plugged into an unattended device doesn't stay open forever.

enable secret Nepal123

Controls entry into privileged EXEC mode. Always prefer enable secret over the older enable password — secret is hashed (MD5) in the config, password is stored in plaintext (or weakly obfuscated by service password-encryption in Step 7).

ip domain-name UniGlobe.com.np
crypto key generate rsa modulus 1024
username admin privilege 15 secret Nepal123

SSH needs a domain name to fold into the RSA key it generates — crypto key generate rsa is the command that actually turns on the SSH server; without a domain name it will refuse to run. modulus 1024 is supplied inline specifically so the command doesn't stop and wait for an interactive prompt, which matters when pasting a config block. privilege 15 gives this local account full administrative rights.

What actually happened on this device On the lab switch used for this session, the same command came back as: 
UniGlobe_Main_Switch_1(config)#crypto key generate rsa modulus 1024
                                    ^
% Invalid input detected at '^' marker.
The command is correct — this is a platform limitation, not a syntax error to fix. Not every switch image (in Packet Tracer or in the real world) ships with the crypto feature set built in; some Layer 2 switch models only support it with a specific IOS image, and some don't support it at all. The lesson is worth keeping rather than editing away: an accepted command is not proof a feature exists on the device in front of you, and the next step below shows exactly how the switch confirms that for itself. 
line vty 0 15
 transport input ssh
 login local
 exec-timeout 5 0
exit
ip ssh version 2

line vty 0 15 configures all 16 remote-login sessions in one shot. transport input ssh blocks Telnet outright — no plaintext remote logins. login local checks the username database from Step 5 instead of a single shared line password. ip ssh version 2 disables the older, weaker SSHv1.

The switch confirms the gap itself ip ssh version 2 was accepted without an error, but the device printed this line right underneath it: 
Please create RSA keys (of at least 768 bits size) to enable SSH v2.
This is the switch politely pointing back at Step 5: the SSH version preference is now stored, but there's still no actual key pair for it to use, since key generation wasn't available on this device. transport input ssh is configured either way — so on real hardware that does support crypto, this whole sequence works exactly as written; the takeaway for a Packet Tracer lab is to always verify with show ip ssh afterwards rather than assuming success from the command prompt alone. 
service password-encryption

Obscures any plaintext passwords still in the config (like the console password from Step 3) so a casual glance at show running-config doesn't reveal them. Worth being honest with students that this is type 7 encryption — reversible in seconds with widely available tools. It raises the bar against shoulder-surfing, not against anyone who actually wants the password.

copy running-config startup-config
! or the shorthand:
write memory

Everything typed so far only exists in running-config, which lives in RAM. See the callout below — this step is the one the actual session never reached.

Reading what the switch prints back at you

Right after end, the switch volunteered three lines nobody typed. These aren't errors — they're the device narrating its own state changes as they happen.

UniGlobe_Main_Switch_1(config)#end
UniGlobe_Main_Switch_1#! Exits all the way back to privileged EXEC mode
%LINK-3-UPDOWN: Interface Vlan1, changed state to down

%LINEPROTO-5-UPDOWN: Line protocol on Interface Vlan1, changed state to up

%SYS-5-CONFIG_I: Configured from console by console

Each follows the same %FACILITY-SEVERITY-MNEMONIC pattern, and the middle number is the useful part:

•

%LINK-3-UPDOWN and %LINEPROTO-5-UPDOWN — Vlan1 briefly toggles as its configuration settles after leaving global config mode; this is routine and self-resolving, not a fault to chase down.

•

%SYS-5-CONFIG_I — a confirmation, generated every single time, that a configuration change was made from this console session. Seeing it is actually the reassuring sign that the preceding steps registered.

The habit worth building here: read the trailing number, not just the words. Lower numbers (0–3) are worth stopping for; a 5 or 6 alongside a routine keyword like UPDOWN or CONFIG_I is the switch keeping a log, not raising an alarm.

Console vs. VTY — two different doors

Both need a password and login, but they protect very different kinds of access.

How you connectProtected byTypical use
Console (con 0) Physical cable, direct to the device Line password + login Initial setup, recovery when the network path itself is down
VTY (0–15) Remote, over the IP network transport input ssh + login local (username/secret) Day-to-day remote administration

running-config vs. startup-config

Two configs exist on every Cisco device, and mixing them up is one of the most common real-world causes of "I configured this yesterday and it's gone":

Where it livesSurvives a reload?How to view it
running-config RAM No show running-config
startup-config NVRAM Yes — it's what loads on boot show startup-config

Recap

1A switch forwards frames with no configuration at all; this page is entirely about administrative access, not forwarding.
2Every command lives in a specific mode — user EXEC, privileged EXEC, global config, or a line/interface sub-mode — and an unrecognized word at any prompt is treated as a hostname lookup, not silently ignored.
3An SVI (interface vlan 1) is where a switch's own management IP lives, and it needs no shutdown like any interface.
4SSH requires a domain name and an RSA key pair before it will run — Telnet on the VTY lines should be disabled once SSH is working.
5running-config is volatile; nothing is permanent until copy running-config startup-config (or write memory) is run.
