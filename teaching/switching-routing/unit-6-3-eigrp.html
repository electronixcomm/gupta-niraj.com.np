Unit 6 · Theory background

EIGRP: the hybrid routing protocol

Enhanced Interior Gateway Routing Protocol (EIGRP) is Cisco's own advanced distance-vector protocol. It borrows link-state habits — formal neighbor discovery, a topology table, bounded triggered updates — while still reasoning the distance-vector way, from a neighbor's advertised numbers rather than a full map of the network.

What this page covers

  • EIGRP's features and why it's called "hybrid"
  • Neighbor discovery and the three tables EIGRP keeps
  • DUAL — reported/feasible distance, successors, feasible successors
  • RTP, the five packet types, and the composite metric formula
  • Configuration basics: AS numbers, auto-summary, passive interfaces, redistribution

1

EIGRP features and operation

EIGRP is a classless protocol that includes the subnet mask in every route update, so it supports VLSM and lets summaries be placed anywhere in the network. Cisco calls it a distance-vector protocol, but also an advanced distance-vector or hybrid protocol, because of traits it borrows from link-state design.

Distance-vector side

  • Sends network + cost from the advertiser's perspective
  • No full link-state packets like OSPF
  • "Routing by rumor" — not every router hears updates firsthand

Link-state side

  • Formal neighbor discovery via Hello
  • Synchronizes topology at startup
  • Sends only bounded updates after that

Scale limits

  • Default hop count 100, max 255
  • Hop count bounds the AS size only — it is not the metric
  • Different ASs don't share routes automatically

Other standout features: supports IP and IPv6 via protocol-dependent modules, considered classless like RIPv2 and OSPF, supports summaries and discontiguous networks, efficient neighbor discovery, communicates via the Reliable Transport Protocol (RTP), selects paths via the Diffusing Update Algorithm (DUAL), reduces bandwidth with bounded updates, and sends no broadcasts.

2

Neighbor discovery and the three tables

Before routers exchange routes they must become neighbors. Three conditions must be met, exchanged via Hello/ACK:

  • Hello or ACK received
  • AS numbers match
  • Identical metrics (K values)

Only when a new neighbor relationship forms does EIGRP advertise its entire routing information; after that, only changes propagate. Each router stores what it learns in three tables:

TableHoldsCommand
Neighbor tableEvery directly connected EIGRP neighbor: IP address, hold time, smooth round-trip timer (SRTT), queue countshow ip eigrp neighbors
Topology tableEvery route advertised by every neighbor — successors and feasible successors, bothshow ip eigrp topology
Routing tableOnly the successor route for each destination — the one actually used to forward trafficshow ip route eigrp
The neighbor and topology tables live in RAM, maintained through Hello and update packets. The routing table is built only from what's in the topology table.
3

DUAL: feasible distance, reported distance, successors

DUAL (Diffusing Update Algorithm) finds backup routes in advance so EIGRP can react to a failure almost instantly, without flooding queries through the whole network.

Reported / advertised distance (RD/AD)

The metric a neighbor reports for a remote network — the neighbor's own routing-table metric to it. This is the second number in the topology table's parentheses.

Feasible distance (FD)

This router's own best total metric: the neighbor's RD plus the cost to reach that neighbor. The lowest FD wins the routing table.

Successor

The route with the lowest FD. Copied into the routing table and used to forward traffic — think "successful."

Feasible successor (FS)

A backup path whose RD is less than the current successor's FD. Stored only in the topology table, ready to replace the successor instantly if it fails.

D 10.0.0.0/8 [90/2195456] via 172.16.10.2, 00:27:06, Serial0/0
    ^AD      ^FD (total cost to 10.0.0.0)

Reading that line: D means DUAL, an EIGRP route. 90 is the administrative distance — easy to confuse with "advertised distance," which is why people often just call it reported distance instead. 2195456 is the feasible distance: the neighbor's reported distance, plus this router's own cost to reach that neighbor.

Feasibility condition
A neighbor's route only qualifies as a loop-free feasible successor if RD < FD — its reported distance must be strictly less than this router's current feasible distance. If no neighbor satisfies that, the route goes active and DUAL must query neighbors for a new path — slower than simply promoting a feasible successor.

Three conditions DUAL depends on to work correctly: neighbors are discovered or declared dead within a finite time (Hello's job), every message is received correctly and in order (RTP's job), and all changes are processed in the order detected.

4

Reliable Transport Protocol and packet types

EIGRP depends on its own proprietary Reliable Transport Protocol (RTP) to manage delivery between neighbors, mixing multicast and unicast. Multicasts go to 224.0.0.10. If a neighbor doesn't reply to a multicast, EIGRP retries via unicast; after 16 failed unicast attempts, that neighbor is declared dead — a process nicknamed reliable multicast. Sequence numbers detect old or out-of-order packets.

PacketDeliveryPurpose
HelloUnreliable multicastDiscovers neighbors; no acknowledgment required
UpdateReliable multicast (unicast if only one router needs it)Carries route information after a metric or topology change
QueryReliable multicastAsks neighbors for an alternate route after losing one
ReplyUnicastAnswers a Query, with a route or "none known"
ACKUnicast, unreliableConfirms an Update — never acknowledged itself, to avoid an endless chain
5

The composite metric

EIGRP weighs up to four factors — bandwidth, delay, load, reliability — plus MTU, which is carried along but never actually used in the calculation. The formula uses tunable K-values:

metric = [K1·BW + (K2·BW)/(256−Load) + K3·Delay] × [K5/(Reliability+K4)]

By default K1 = K3 = 1 and K2 = K4 = K5 = 0, which collapses the formula to:

metric = lowest bandwidth along the path + sum of all delays along the path
  • Bandwidth = [10,000,000 / (bandwidth in Kbps)] × 256 — the lowest bandwidth link in the path is what counts, not a sum.
  • Delay = [delay in tens of microseconds] × 256 — this one is summed along the whole path.
K-values must match exactly between neighbors — a mismatch is a common reason an adjacency never forms, even when AS numbers and addressing are correct. Adjust them only under vendor guidance; changing defaults can cause instability.

Configuring EIGRP

Two configuration modes are used: router configuration mode enables the protocol, chooses networks, and sets global factors; interface configuration mode tunes bandwidth, summaries, and passive behavior.

Router(config)# router eigrp 20                 ! AS number — must match on every neighbor
Router(config-router)# network 10.0.0.0             ! classful — enables every matching interface
Router(config-router)# network 172.16.0.0
Router(config-router)# eigrp router-id 1.1.1.1      ! optional; less critical than in OSPF
Router(config-router)# passive-interface g0/2       ! stops Hellos; network is still advertised
Router(config-router)# no auto-summary             ! disable classful summarization — see next section

The AS number is only locally meaningful in the sense that its value doesn't matter (1–65,535) — but every router in the same EIGRP domain must use the same number, or no adjacency forms at all. A wildcard mask can narrow a network statement the same way it does in OSPF, but most EIGRP designs just use the classful form and rely on passive-interface to stop Hellos where they're not wanted.

The passive-interface command behaves differently here than under RIP: an EIGRP interface marked passive neither sends nor reads Hellos, so no adjacency can ever form there — but the network is still advertised to everyone else.
7

VLSM, summarization, and discontiguous networks

EIGRP supports VLSM because the subnet mask travels with every route. It also auto-summarizes at classful boundaries by default in pre-15.0 code (15.x disables it by default, but the exam still expects you to know why it matters). The danger: if the same classful network is split across two sites separated by a different major network — a discontiguous network — every site injects a conflicting summary, and routing breaks.

D 172.16.0.0/16 is a summary, 00:01:37, Null0   ! two different sites both do this — collision

The fix is always no auto-summary on every router in the discontiguous design. Manual summarization at specific, well-chosen points is still fully supported and often a good idea — it's automatic classful summarization across a discontiguous boundary that causes the outage.

8

Load balancing and split horizon

Equal-cost

Up to 4 paths by default (same as RIP and OSPF), configurable up to 32 (16 on pre-15.0 code) with maximum-paths.

Unequal-cost

EIGRP alone among these three can balance across unequal paths using variance. A variance of 2 includes any feasible successor with FD up to twice the successor's — traffic still shares proportionally to cost, not evenly.

Split horizon

Enabled by default: a route learned on an interface is never advertised back out that same interface. Usually helpful, but causes trouble on point-to-multipoint hub links — subinterfaces are the usual fix.

  • Interfaces between the devices are down
  • Mismatched AS numbers
  • Proper interfaces aren't enabled for EIGRP
  • An interface is passive
  • K-values don't match
  • Authentication is misconfigured

EIGRPv6 quick reference

EIGRPv6 keeps the same algorithm (DUAL), the same reliability layer (RTP), and the same composite metric — the differences are all about addressing. There's no network command: EIGRPv6 is enabled directly, per interface.

Router(config)# ipv6 unicast-routing
Router(config)# ipv6 router eigrp 10
Router(config-rtr)# no shutdown            ! the process itself must be enabled
Router(config-rtr)# router-id 1.1.1.1
Router(config)# interface g0/0
Router(config-if)# ipv6 eigrp 10            ! enables EIGRPv6 on this interface only
  • Multicast address changes from 224.0.0.10 to FF02::A.
  • No network statements, so no passive-interface headaches either — if an interface isn't enabled, it's simply not part of the process.
  • Router ID matters far less than in OSPF; it's set under the global ipv6 router eigrp command since there may be no IPv4 address to derive one from.
  • Neighbor and next-hop addresses are always link-local, never the routed global address.

The real-world choice is almost always OSPF vs. EIGRP — and that usually comes down to two questions: is the network single-vendor (Cisco) throughout, and is a formal area hierarchy worth the extra design and documentation effort it demands.

Self-check

1. What's the difference between reported distance and feasible distance?
Reported distance is the neighbor's own metric to the destination. Feasible distance is this router's total cost — the neighbor's reported distance plus the cost to reach that neighbor. The lowest FD becomes the successor.
2. Why would a feasible successor not exist for a given route?
If no neighbor's reported distance is less than the current feasible distance, the feasibility condition fails for all of them, so DUAL has no safe backup — the route goes active and queries are sent out.
3. Two EIGRP routers won't form an adjacency even though IPs, masks, and AS numbers all match. What else should you check?
K-values. They must be identical on both sides — this is one of the three conditions for neighbor formation, and it's easy to overlook since it doesn't show up as an addressing or AS mismatch.
4. A network has 172.16.1.0/24 on one site and 172.16.2.0/24 on another, connected through a 10.0.0.0/8 backbone. What EIGRP-specific problem does this risk, and what's the fix?
A discontiguous network — both sites auto-summarize to 172.16.0.0/16 by default and inject conflicting summaries. Fix: no auto-summary on every router in the design.
5. What makes EIGRP capable of unequal-cost load balancing when RIP and OSPF aren't?
The variance command, which allows any feasible successor with a feasible distance up to a multiple of the successor's FD to also be installed and used, proportionally to its cost.
