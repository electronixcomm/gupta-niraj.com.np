The MAC address table, and how a switch decides where a frame goes

A switch never has to be told which device sits on which port — it figures that out for itself, purely by watching traffic. This unit is about how that table gets built, how it goes stale, and the three things a switch can do once it's looked a destination MAC up.

How the table is learned

The switch never inspects the destination MAC to learn anything. Learning only ever happens from the source MAC of an arriving frame.

1

A frame arrives on a port — any port, any frame, it doesn't matter what kind.

2

The switch reads the source MAC address in the frame header.

3

It checks its table: is this source MAC already recorded? If not, it adds a new row: source MAC → the port it just arrived on.

4

If the MAC is already there, the switch just resets its aging timer — proof the device is still active on that port.

Why this matters The table only ever reflects devices that have transmitted something. A device that's been silent — even if it's powered on and perfectly reachable — simply won't have an entry until it sends its first frame.

Aging: why entries disappear

Cisco switches default to a 300-second (5-minute) aging timer per dynamically learned entry.

Every time a frame arrives with a source MAC that's already in the table, that entry's timer resets to 300 seconds. If 300 seconds pass with zero frames from that MAC, the entry is silently deleted — not because the device is gone, but simply because the switch hasn't heard from it recently enough to keep assuming where it lives.

This is exactly what creates the scenario from earlier: 6 minutes of silence from PC-B is enough to age its entry out, even though PC-B never actually went anywhere.

The forwarding decision

Once a frame's destination MAC has been read, the switch has exactly three possible moves.

Is the destination MAC a broadcast (FFFF.FFFF.FFFF) or multicast address?
yes →
outcome Flood out every port except the source — mandatory, table is never even checked
no ↓
Is the destination MAC in the table?
no →
outcome Unknown unicast flood — send out every port except the source, as a fallback
yes ↓
Is that port the same one the frame arrived on?
yes →
outcome Filter — drop the frame, destination is already on that segment
no →
outcome Forward — send out that one port only

Two different reasons to flood

Same physical action — out every port but the source — for two very different reasons.

Who chose the destinationWhat triggers itSelf-corrects?
Unknown unicast flood Source host, via a resolved MAC (e.g. from ARP) Destination MAC is a real unicast address, just not yet in the table Yes — one reply from the destination teaches the switch, future frames forward directly
Broadcast flood Source host, intentionally addressing "everyone" Destination MAC is exactly FFFF.FFFF.FFFF No — it will flood every single time, forever; there's no real MAC to ever learn

Two things worth pointing out to students who expect to see a MAC table sitting somewhere in this config:

1

The MAC address table is not part of the running-config at all. It isn't a setting anyone typed in — it's a dynamic, in-memory table the switch builds itself by watching traffic, exactly as described above. That's why show running-config lists 24 FastEthernet interfaces and 2 Gigabit interfaces with essentially nothing configured on any of them, yet the switch is still perfectly capable of learning and forwarding on all of them the moment frames start arriving.

2

To actually see the table this unit has been describing, the command is show mac address-table (or the older show mac-address-table) — not show running-config. Have students run it after PC-A pings PC-B and compare what shows up against the CAM table in the simulator above.

In-class exercise On UniGlobe_Main_Switch_1, have students predict the output of show mac address-table before any host has sent traffic (empty — nothing has been learned yet, VLAN1's own IP doesn't create an entry), then again right after a ping between two attached PCs. The single new pair of rows that appears is the same source-MAC-triggered learning event walked through step-by-step earlier on this page.

Recap

1The MAC table is built only from source MACs of arriving frames — never from destinations.
2Entries age out after 300 seconds of silence from that MAC — this doesn't mean the device is gone, just unheard-from recently.
3Every frame gets one of three outcomes: forward (known, different port), filter (known, same port), or flood (unknown, or broadcast/multicast).
4Unknown unicast flooding is temporary and self-correcting; broadcast flooding is permanent by design.
5An aged-out CAM entry never breaks connectivity — the very next frame the "missing" device sends re-teaches the switch instantly.
